\begin{abstract}
Legacy-code translation tools can produce plausible target programs while obscuring
which source constructs were handled and what was actually checked. We demonstrate a
compiler-design prototype that translates declared subsets of COBOL, FORTRAN, Pascal,
and line-numbered BASIC into JavaScript or Python, and a project-specific Python-like
subset into JavaScript. Its web interface exposes tokenization, normalized intermediate
data, deterministic output, unsupported constructs, optional complete-program model
proposals, and finite validation results. The model output remains an unaccepted
candidate. On the current 23-case, five-group pilot, both targets passed all 19
supported cases and matched their expected outputs; all four expected-unsupported
cases (three COBOL loops and one CodeNet Fortran array-input program) were recognized.
The supported CodeNet scalar-input programs passed 17 and five predeclared fixtures on
both targets, respectively, and native Fortran builds; the array-input program passed four native fixtures. The other
expected outputs have not been checked against native source compilers. The historical
paired model benchmark returned no candidate;
a later fixed, single-input trial generated JavaScript and Python candidates that each
matched one predeclared expected output. Both remain unaccepted pending review. The
prototype demonstrates inspectable boundaries, not an effectiveness gain or general
semantic equivalence.
Demonstration video: \url{[PUBLIC_YOUTUBE_VIDEO_URL]}
\end{abstract}

\section{Introduction}
Modernizing legacy code requires more than producing syntactically plausible output:
users need to know which constructs were translated, where behavior is uncertain, and
what evidence supports a candidate. Prior translation systems combine code generation
with execution, testing, or explicit feature analysis in their evaluated settings
\cite{yang2024,zhang2025}. Our contribution is narrower: a runnable teaching/research
prototype whose interface makes its declared subset and validation boundary visible.

The prototype does not establish a new translation algorithm, full language coverage,
or an effectiveness advantage. It provides (1) custom subset front ends and a shared
normalized representation, (2) deterministic rule-first translation, (3) optional
complete-program LLM proposals for unsupported input, and (4) finite target execution
and separately authored output checks. It is intended for researchers and students
inspecting translation decisions, not production migration teams.

\section{Tool and Demonstration}
The front ends recognize documented subsets of COBOL, FORTRAN, Pascal, BASIC, and a
project-specific Python-like language. The first four languages can target JavaScript or
Python; the Python-like demonstration path targets JavaScript. This is not full-dialect
support. The normalized representation and deterministic code generator expose the
rule-based path. Parser-reported unsupported input can trigger an optional request for
a complete target program. The application retains deterministic partial output,
displays the model candidate separately, reports candidate syntax/runtime status, and
never marks the candidate semantically accepted.

The demonstration uses a held-out maximum-of-two-numbers case from the test split.
The user selects COBOL and JavaScript, pastes the source in Fig.~\ref{fig:walkthrough},
and presses \emph{Translate}. The UI's stage indicators lead into the token and shared-IR
inspectors; the generated-code pane shows the deterministic branch, while the status
and metrics report a successful target run. For this concrete input ($A=17$, $B=25$),
the target prints \texttt{25}, matching the case's separately authored expected output.
The case is task-derived and adapted to fixed values; it is not evidence about arbitrary
COBOL programs.

The second step loads the COBOL fallback example from \emph{More actions}. It contains
\texttt{CALL "EXTERNAL-ROUTINE"}, outside the declared subset. The UI reports the
unsupported construct, keeps deterministic output separate from any model proposal,
and shows fallback status. In the recorded v3 refresh the provider returned no
candidate after three attempts per target, so the demonstration explicitly shows that
failure state rather than implying that fallback always produces usable code. The
benchmark view can then display per-case outcomes; unsupported recognition is distinct
from translation success. The complete source is treated as untrusted prompt content.

JavaScript candidates are syntax-checked and executed using Node's permission mode,
with a timeout and a reduced child environment. Python candidates are syntax-checked
and, when Docker is available, run in an isolated no-network, read-only container with
resource limits. A separate Python trial report records three fixture-variant matches;
the COBOL source layout remains unspecified and has not been compiler-checked. Neither
runtime path is a complete security sandbox or semantic acceptance gate. The current
[candidate acceptance policy](documentation/CANDIDATE_ACCEPTANCE.md) requires independent evidence
and human review before any candidate could be accepted.

\section{Evaluation and Limitations}
We ran the deterministic benchmark against JavaScript and Python. The test split has
23 records in five task groups: maximum-of-two-numbers, for-loop, CodeNet p02600,
CodeNet p02606, and CodeNet p02607. It contains 19 expected-translatable records and four expected-unsupported records
(three COBOL \texttt{PERFORM} cases and one Fortran array-input case). The 19 supported
target executions matched their separately authored expected outputs in both targets
(19/19); all four unsupported cases were recognized (4/4). End-to-end status was 19/23
for each target because expected-unsupported
cases are reported as \texttt{not\_run}, not translation passes (Table~\ref{tab:results}).

The 20 project-authored task cases' expected outputs are derived from fixed constants
and loop ranges and match a separate reference evaluator (20/20). CodeNet p02600 passed
two official samples and 15 interval fixtures under GNU Fortran 14.3.0, and its source
translated on all 17 fixtures for both targets. CodeNet p02607's two official and two
derived fixtures also pass GNU Fortran 14.3.0. CodeNet p02606's three official and two
derived fixtures pass the same compiler and its translation passes all five fixtures
on both targets. These local builds do not reproduce the
metadata-listed GNU Fortran 9.2.1 environment. No second human reviewed the oracle. The
corpus has only five test task groups and is not a representative estimate of
translation accuracy. The original
24-case paired refresh at pushed commit \texttt{ade68dc} used
\texttt{gemini-3.1-flash-lite} and \texttt{legacy-modernizer-llm-v3}. The provider
returned no candidate after three request attempts for the unsupported case in each
target. In a later single-input provider smoke trial, JavaScript and Python candidates
were generated and matched the one fixed expected output; both remain unaccepted. The
The current guarded five-repeat v6 ablation used the 23-case corpus. CodeNet inputs were
withheld from the provider, and all 15 eligible project-authored requests per target
failed with connection errors, producing no candidates. All arms scored 95/115 case-runs;
learned-rule reuse was zero, and reviewer effort was not measured. This is not evidence
of LLM effectiveness. A preserved v4 attempt included CodeNet requests; payload receipt
is unknown. Independent source/oracle/license reviews for CodeNet cases remain pending.

Contract and risk checks gate finite-test eligibility and rule storage; learned-rule
memory reuses only matching templates. No controlled ablation has shown that these
mechanisms improve correctness or review time. We make no scalability or multilingual-bias claim. Native source-language oracles,
a larger task-grouped corpus, independent human review, and repeated controlled model
trials remain future work. The complete run provenance and case JSON
are linked in the repository's \texttt{data/EVIDENCE\_V3\_REFRESH.md}.

\section{Availability}
The source and usage instructions are publicly available at
\url{https://github.com/yoshi-hue/transpiler}. The tool runs locally using Python,
FastAPI, and Uvicorn; the README documents installation, configuration, and execution.
The optional model provider must be configured by the user. No API credential is
included in the artifact.
